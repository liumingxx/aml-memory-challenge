| **v0.3** | **本版本**：针对 v0.2 smoke 中最弱的三项（记忆治理 20.00 / 多跳推理 33.33 / 上下文学习 30.00）做定向优化，并吸收了 Mem0 框架的公开设计思想（原子事实、多路信号、显式记忆维护），但**全部以确定性算法实现**。**仍不含任何生成式模型，无第三方依赖。** |

## 1. 系统定位

本系统只实现比赛规定的两类记忆操作：

- **Add**：接收评测记忆，完成持久化、组织与索引
- **Search**：按问题返回相关记忆证据，按相关性排序

**不参与答案生成与评分**；平台返回的候选记忆由评测平台统一的 Answer / Eval 流程处理。

核心设计原则：**Add 返回 200 时，记忆必须已经落盘并且立即可检索。**

---

## 2. 数据流

```
平台 ──Add──▶ 校验 → 相对时间归一化 → 分句入列 → 生成相邻消息窗口 → 写入 SQLite
                                                          │
平台 ──Search─▶ 多路检索（关键词 / 选项扩展 / 可选向量）→ RRF 融合 → MMR 去重 → Top-K 原文
```

## 3. 关键技术选择

### 3.1 存储：单机 SQLite（WAL 模式）

| 考虑 | 说明 |
| --- | --- |
| 为什么不用向量数据库 | 检索被限制在单个 `user_id` 作用域内（一个对话/样本），候选量级为数百到数千条，SQLite + 内存计算即可满足延迟要求 |
| WAL 模式 | 允许读写并发，写入不阻塞检索 |
| 幂等设计 | `requests` 表以 `request_id` 为主键；记忆表对 `(user_id, fingerprint)` 建唯一约束。平台按同一 `request_id` 重试时不会产生重复记忆 |
| 持久化 | 每次 Add 显式 commit 后才返回 200；数据文件位于磁盘，进程重启后数据完整 |

### 3.2 分词与词形归一化（纯文本处理）

- 英文/数字：按 `[a-z0-9]+` 提取词元，再做**轻量后缀还原**（`work` / `works` / `working` / `worked` 归一为同一检索键），使问句与记忆的时态/单复数差异不再导致漏检
- 中文/日文/韩文：取字符 unigram + bigram

选择理由：不引入分词或词干化依赖即可获得可用的中英检索效果，保持"零第三方依赖"的部署属性。

### 3.3 多尺度相邻消息窗口索引

长对话中的事实经常**分散在多条消息里，且后续消息使用代词指代**。若只索引单条消息，这类问题无法被检索到。

因此除单条消息外，系统额外为每条消息生成**多个尺度的滑动窗口行（2 / 3 / 5 条消息）**（窗口可跨请求边界，通过读取同一 `session_id` 的尾部消息续接）：

```
[2026-03-15] user: My sister Lan just moved to Hangzhou.
[2026-03-15] assistant: That is a big change for her.
[2026-03-15] user: Yes. She now works at a bank near West Lake.
```

不同尺度覆盖不同距离的多跳：2 条窗口处理简单的追问，5 条窗口可以把"Lan 搬到杭州 → 她之前在南京当老师"这类跨 4 条消息的因果链装进**同一个自包含检索单元**。

问题 "Where does Lan work?" 需要把 `Lan` 与 `bank` 两条消息连起来；窗口行把二者合并成一个**自包含的检索单元**，因此能排到第 1 位，而单条消息（"She now works at a bank"）缺少主体信息、无法独立回答问题。同理，"Where did Lan work **before** she moved to Hangzhou?" 需要跨越第 1 条与第 5 条消息，5 条窗口能够一次命中。

### 3.4 相对时间归一化（本版本新增）

记忆原文常写 "yesterday"、"last month"、"三周前"、"去年"，而问题可能问具体日期（或反之）。系统在写入时把这些相对表达**按消息时间戳换算成绝对日期**并追加到索引文本：

```
原文：My sister Lan moved to Hangzhou yesterday.   （时间戳 2026-03-15）
索引：… resolved 2026-03-14 2026 3 14
```

这样用 `2026-03-14` 检索可以命中该条记忆。所有换算均为确定性日期运算，无模型参与。

### 3.5 检索与排序

1. **BM25**（k1 = 1.2，b = 0.75），索引文本中同时注入消息时间与归一化后的日期词元
2. **覆盖率加权**：命中查询词元的比例越高加权越高（最多 +35%），避免"只命中一个词"的文档压过"命中多个词"的文档
3. **多路检索 + RRF 融合**（Reciprocal Rank Fusion，k = 60）：
   - 第 1 路：原问题检索（权重 1.0）
   - 第 2 路：问题 + 选择题选项文本检索（权重 0.6，仅在平台下发 `options` 时启用）
   - 第 3 路（可选，默认关闭）：向量检索（权重 1.0）
4. **MMR 去重**（Maximal Marginal Relevance，λ = 0.82）：避免 Top-K 被"窗口行 + 其组成消息"这类近重复内容占满，把名额让给信息量更不同的记忆
5. **窗口行轻微加权**（×1.04）：窗口比单条消息更自包含，同分时优先
6. **默认偏向当前事实的时效加权**（v0.3 新增）：先在问题里检测是否**明确指向过去**（年份、`used to / before / previously / 以前 / 当时` 等）。指向过去时几乎不加时效权重；否则默认按"问的是当前状态"处理，对较新记忆施加 +30%（含 `now / currently / 现在 / 目前` 等现在时标记时 +40%），按 365 天常数衰减。这样"当前住址"会优先取用最新记忆，而"2023 年住哪"仍能被时间匹配命中
7. **时效补位**（v0.3 新增）：词面向量无法把"Where do you live?"与"I moved to Shanghai"联系起来——两者没有任何共同词，后者得分会是 0 而被直接排除。由于 `top_k = 100` 而单会话通常只匹配到几十条，**剩余名额用于补入最新的若干条消息**（默认最多 25 条，仅对非历史问题启用，排在已匹配结果之后）。平台回答环节的规定是"记忆冲突时优先采用最新的那条"，因此这些名额对事实更新类问题有直接价值
8. **时效感知的 MMR**（v0.3 新增）：一个候选只有在"与**比它更新**的已选记忆重复"时才被降权。因此新版事实不会被旧版的重述挤下去，而旧版的重述会让位给新版
9. **句子级原子事实**（v0.3 新增，学自 Mem0 的 "one memory = one fact"）：长消息按句切分，每一句独立成条（`kind = sent`），使一条消息里包含的多个事实可以分别被检索到
10. **实体加权**（v0.3 新增，学自 Mem0 的多路检索信号）：从问题中提取**专有名词与年份**，命中这些实体的记忆获得最多 +30% 加权。多跳问题通常依赖人名/地名的正确关联

### 3.6 输出约束

- 返回条数严格 `≤ top_k`
- `data` 为数组，无额外包装层；无结果返回 `[]`
- 每条记录包含非空 `id`（稳定标识）与 `content`
- `content` 默认带 `[YYYY-MM-DD]` 日期前缀（单条消息），便于平台 Answer 流程处理时序问题；窗口行本身已按行携带日期，不重复添加
- 保留接口返回顺序，供平台 Answer 流程按序取用

### 3.7 隔离与安全

- `user_id` 是唯一的检索作用域，Add 与 Search 必须一致；**禁止跨 `user_id` 返回记忆**
- 鉴权支持 `Bearer` / `Token` / `X-Api-Key`
- 错误响应采用 `{"detail": {"reason": "..."}}` 结构，不泄漏内部实现与密钥
- 日志只记录方法、路径、状态码与耗时，**不记录请求正文**

## 4. 模型使用声明

**本系统在 Add 与 Search 全过程中不调用任何生成式大模型。**

- 全部检索逻辑为确定性算法与文本处理：BM25、字符 n-gram、滑动窗口拼接、日期运算、后缀还原、RRF、MMR
- 代码中不存在任何大模型 SDK 的引用（无 `openai`、`anthropic`、`langchain` 等依赖）
- 因此不涉及平台关于"Add / Search 过程中使用的模型必须为 gpt-4o-mini"的限制条款
- `/health` 接口直接返回 `"generative_model_used": false`，便于核验

**向量层（默认关闭）**：代码保留了一个可选的本地 Embedding 检索分支（环境变量 `EMBED_BACKEND`），默认值为 `none`（关闭）。Embedding 模型不是生成式模型，但仍保持默认关闭，以采用最保守的合规姿态。如后续启用，将以新版本申报并同步更新本说明。

**采纳的设计思想（均以确定性算法独立实现）**

| Mem0 的设计 | 本实现的落地方式 | 对应代码位置 |
| --- | --- | --- |
| 「一条记忆 = 一个事实」（原子事实抽取） | **句子级索引**：长消息按句切分，每句独立成条；不使用任何模型做事实抽取 | `split_sentences()` |
| 多路检索信号（语义 + 关键词 + 实体） | **实体加权**：从问题中提取专有名词与年份，命中者获得最多 +30% 加权；不引入语义模型，仅在关键词一路之外增加实体一路 | `query_entities()` / `ENTITY_BOOST` |
| 显式记忆维护（ADD / UPDATE / DELETE / NOOP） | **检索期的时效策略**：默认偏向当前事实（非历史问题 +30%，含现在时标记 +40%），并对明确指向过去的问题（年份、used to、以前等）几乎不加权；另设"时效补位"以补回被词面匹配排除的最新记忆 | `query_recency_strength()` / `RECENCY_TAIL` |

**明确放弃的部分及原因**

| Mem0 的做法 | 为什么本实现不采用 |
| --- | --- |
| 写入时用大模型判定 ADD / UPDATE / DELETE / NOOP | ① 会引入生成式模型调用，受平台"Add/Search 中的模型必须为 gpt-4o-mini"条款约束，并带来复现分数不稳定的风险；② 实测表明**纯字符串方法无法可靠识别语义级事实冲突**——例如 `I live in Beijing` 与 `I just moved to Shanghai` 的字面重合度仅约 0.45，硬做会产生大量误判 |
| 对失效记忆执行 **DELETE** | 本评测会提出历史性问题（如"2023 年住在哪里"）。因此本实现**从不删除任何记忆**，改为在检索期按问题的时间意图调整排序，使新旧事实都能被召回 |
| 依赖向量库 / 图数据库 / 外部 LLM API | 为保持零第三方依赖、零成本与可复现性，本实现只使用 Python 标准库与单机 SQLite |

**结论**：本实现与 Mem0 不存在代码层面的复用关系，因此不构成 Apache-2.0 意义上的衍生作品；本仓库继续采用 MIT 许可证。上述引用系依据赛事"复用他人论文或仓库必须披露原作者、技术报告与全部方法改动"的要求主动作出。

## 6. 性能与局限

### 实测性能（本地复现环境，2 核 2 GiB）

| 场景 | 结果 |
| --- | --- |
| 单会话约 4,000 条记忆（1000 条消息 + 2993 个多尺度窗口），`top_k = 100` | 检索约 0.38 秒 |
| 单会话约 6,000 条记忆，`top_k = 100` | 检索约 0.74 秒 |
| 单次 Add 写入 300 条消息 | 约 0.09 秒 |
| 空载内存占用 | 约 10–20 MB |

### 已知局限

| 局限 | 影响 | 后续计划 |
| --- | --- | --- |
| 仅做字面/词形匹配，缺少语义匹配 | 问题与记忆用词差异较大时召回不足 | 视合规确认结果，考虑启用本地非生成式 Embedding 层（代码已就位，默认关闭） |
| 未做事实抽取与指代消解 | 跨消息指代主要靠窗口缓解，超过 5 条消息距离的指代仍可能漏 | 窗口尺度可配置（`WINDOW_SIZES`）；进一步方案受模型规则限制，暂不实施 |
| 冲突消解依赖"现在时"关键词识别 | 若问题未含时间标记，时效权重回落到默认档位 | 可扩充 `RECENCY_INTENT` 词表 |
