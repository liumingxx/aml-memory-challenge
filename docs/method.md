# 方法说明

> 参评赛道：文本记忆（Textual Memory）
> 参评组别：开源方法榜（Open-source Methods）
> 系统版本：v0.1（BM25 基线版）
> 参赛团队：柳明溪、符莹莹（两人团队）

---

## 1. 系统定位

本系统只实现比赛规定的两类记忆操作：

- **Add**：接收评测记忆，完成持久化、组织与索引
- **Search**：按问题返回相关记忆证据，按相关性排序

**不参与答案生成与评分**。平台返回的候选记忆由评测平台统一的 Answer / Eval 流程处理。

核心设计原则：**Add 返回 200 时，记忆必须已经落盘并且立即可检索。**

---

## 2. 数据流

```
平台 ──Add──▶ 切分消息 ──▶ 写入 SQLite（原文 + 时间 + 角色）
                              │
平台 ──Search─▶ 构造查询 ──▶ BM25 打分排序 ──▶ 返回 Top-K 原文
```

## 3. 关键技术选择

### 3.1 存储：单机 SQLite（WAL 模式）

| 考虑 | 说明 |
| --- | --- |
| 为什么不用向量数据库 | 检索被限制在单个 `user_id` 作用域内（一个对话/样本），候选量级为数百到数千条，SQLite + 内存计算即可满足延迟要求 |
| WAL 模式 | 允许读写并发，写入不阻塞检索 |
| 幂等设计 | `requests` 表以 `request_id` 为主键；记忆表对 `(user_id, fingerprint)` 建唯一约束，平台按同一 `request_id` 重试时不会产生重复记忆 |
| 持久化 | 每次 Add 显式 commit 后才返回 200；数据文件位于磁盘，进程重启后数据完整 |

### 3.2 分词：拉丁词 + CJK 字符 bigram

- 英文/数字：按 `[a-z0-9]+` 提取词元
- 中文/日文/韩文：取字符 unigram + bigram

选择理由：bigram 无需引入分词依赖即可获得可用的中文检索效果，避免第三方库带来的部署复杂度；对"字面不同但用词接近"的查询也有一定鲁棒性。

### 3.3 排序：BM25 + 时间加权

- 采用标准 BM25（k1 = 1.2，b = 0.75）
- 索引文本中注入时间信息：将 `timestamp`（Unix 毫秒）同时展开为 `YYYY-MM-DD`、"月份 年份"、年/月/日等词元，使"什么时候发生的"这类时序问题可被词面命中
- 对较新的记忆施加轻微加权（`1 + 0.05 / (1 + age_days / 365)`），用于打破同分时的平局；不会丢弃旧记忆

### 3.4 输出约束

- 返回条数严格 `≤ top_k`
- `data` 为数组，无额外包装层；无结果返回 `[]`
- 每条记录包含非空 `id`（稳定标识）与 `content`（原始记忆文本）
- 保留接口返回顺序，供平台 Answer 流程按序取用

### 3.5 隔离与安全

- `user_id` 是唯一的检索作用域，Add 与 Search 必须一致；**禁止跨 `user_id` 返回记忆**
- 鉴权支持 `Bearer` / `Token` / `X-Api-Key`
- 错误响应采用 `{"detail": {"reason": "..."}}` 结构，不泄漏内部实现与密钥

## 4. 模型使用声明

**本系统在 Add 与 Search 过程中不调用任何生成式大模型。**

当前版本为纯检索实现（BM25 + CJK bigram），检索链路中不包含任何 LLM 调用，因此不涉及平台关于"Add / Search 过程中使用的模型必须为 gpt-4o-mini"的限制条款。

后续如引入向量检索，将使用自托管的 Embedding 模型作为索引组件（平台文档明确说明不规定 embedding 模型与内部架构），并在版本说明中同步披露。

## 6. 已知局限与后续计划

| 局限 | 影响 | 后续计划 |
| --- | --- | --- |
| 仅字面匹配，缺少语义匹配 | 问题与记忆用词差异较大时召回不足 | 引入自托管 Embedding，做 BM25 + 向量混合检索（RRF 融合） |
| 未做事实抽取与记忆治理 | 长对话中的指代、相对时间无法归一化 | 评估后视情况引入，并严格遵循模型使用规则 |
| 未做重排 | 排序精度有提升空间 | 对 Top-N 候选加一层 rerank |
